OpenXLA: Compiling AI Models with HLO Representations

OpenXLA streamlines artificial intelligence model execution by translating diverse framework code into a unified High-Level Optimizer (HLO) intermediate representation. This article provides a direct look at how OpenXLA ingests AI models, applies hardware-agnostic and target-specific optimizations using HLO, and ultimately generates high-performance machine code for various hardware backends like CPUs, GPUs, and TPUs.

Ingesting Framework Models into StableHLO

The compilation process begins at the framework level. Developers write AI models in high-level frameworks such as PyTorch, TensorFlow, or JAX. Instead of building custom compilers for every combination of framework and hardware, OpenXLA uses a portable layer called StableHLO.

StableHLO acts as a bridge. The AI framework exports the model's computation graph into a StableHLO representation. This step ensures backward and forward compatibility, decoupling the rapid evolution of frontend frameworks from the backend compiler technologies. Once inside the OpenXLA ecosystem, StableHLO is lowered directly into the internal XLA HLO format.

The Role of the High-Level Optimizer (HLO)

HLO is the core intermediate representation (IR) within the OpenXLA compiler. It represents the AI model as a statically typed, functional dataflow graph made of mathematical operations—such as matrix multiplications, convolutions, and element-wise additions—operating on multidimensional arrays (tensors).

By stripping away framework-specific abstractions, HLO gives the compiler a pure mathematical view of the model. This makes it possible to analyze dependencies, memory requirements, and execution order with high precision.

Target-Independent Optimizations

Once the model is in the HLO format, OpenXLA runs a series of target-independent optimization passes. These optimizations improve the efficiency of the computation graph regardless of the final hardware destination. Key passes include:

  • Dead Code Elimination: Removes operations whose results are never used.
  • Algebraic Simplification: Replaces complex mathematical sequences with simpler, equivalent operations (e.g., multiplying a tensor by zero).
  • Common Subexpression Elimination: Identifies identical computations and alters the graph to calculate them only once.
  • Constant Folding: Calculates operations with known constant inputs at compile time rather than runtime.

Target-Specific Optimizations and Operator Fusion

After general cleanup, OpenXLA transitions to target-specific HLO passes. At this stage, the compiler considers the architecture of the target hardware (such as an NVIDIA GPU, an AMD GPU, or a Google TPU).

The most critical optimization here is Operator Fusion. AI models are frequently bottlenecked by memory bandwidth—the time it takes to move data back and forth between the processor's compute units and the main memory (VRAM or RAM).

OpenXLA analyzes the HLO graph and groups multiple sequential operations into a single "fused" HLO instruction. For example, if a matrix multiplication is immediately followed by a bias addition and a ReLU activation, OpenXLA fuses them. The hardware can then execute all three operations in one pass, keeping the intermediate data in fast, on-chip registers rather than writing it back to slow main memory.

During this phase, the compiler also performs layout assignment, altering how multi-dimensional tensors are arranged in physical memory to match the optimal access patterns of the specific hardware backend.

Code Generation for Diverse Hardware Backends

Once the HLO graph is fully optimized and fused, OpenXLA lowers the HLO into machine-specific code. Because HLO has already resolved high-level graph structure and memory layouts, the backend compilers can focus strictly on instruction scheduling and register allocation.

OpenXLA routes the optimized HLO through different pathways depending on the hardware:

  • CPUs and GPUs: OpenXLA translates the HLO into LLVM IR. From there, the LLVM compiler infrastructure generates the final native machine code, such as x86/ARM assembly for CPUs, PTX for NVIDIA GPUs, or AMDGPU instructions for AMD hardware. For specific matrix operations, OpenXLA may also bypass code generation to call highly tuned vendor libraries like cuBLAS or cuDNN directly.
  • TPUs and Custom Accelerators: Hardware vendors use the optimized HLO to target their proprietary compiler backends, translating the fused HLO operations directly into instructions for systolic arrays and custom vector units.

By separating the compilation pipeline into StableHLO ingestion, HLO graph optimization, and backend-specific lowering, OpenXLA allows any AI framework to run efficiently on any supported hardware without requiring manual kernel engineering.
